    <typescript>
      TypeScript — основной инструмент контроля качества. Соблюдаем естественную типизацию:
      
      - По умолчанию — inference. Явный тип объявляем только когда он добавляет ограничение.
      - Тип добавляет ограничение, если (любое из):
        - Структура отличается от источника (скрытие полей, переименование, вычисляемые поля);
        - Тип входит в Public API slice'а;
        - Это дискриминирующий union для результатов/статусов.
      - Тип не добавляет ограничение, если он 1:1 повторяет вывод другого выражения (запрос к БД, return другой функции) — используй inference, чтобы не дублировать источник правды.
      - При объявлении составного типа — размещаем его сверху; типы, на которые он ссылается, — ниже. Читатель сначала видит целое, затем детали.

      - Запрещены `any`, `as Foo`, non-null `!`.
      - `as const` — только для литералов, когда без него типы хуже.
      - `satisfies` — только если без него ломается типизация или хуже читабельность.
      - `type`, не `interface`.
      - Не экспортировать неиспользуемое. Локальные типы лаконичны: `Params`, не `FunctionNameParams`.
      - Параметры >2–3 или нетривиальной формы — отдельный `type Params` над функцией (`type Props` для React-компонентов).
      - В Public API slice'а (экспорт из `index.ts`) — явные, самодостаточные типы: тот, кто импортирует, видит структуру без перехода в другие файлы. Запрещены `ReturnType`, `Parameters`, цепочки `Pick`.
      - Результаты/статусы — дискриминирующие union'ы (`{ type: "..." }`) + exhaustiveness через `never`.

  <app-architecture>
    Конкретные слои, сегменты и локальные правила определяются в `docs/code-gen/{id}.md`.
    При генерации кода для любого `@apps/*` или `@packages/*` — всегда используй core.md + соответствующий файл.


    1. Соблюдаем однонаправленность зависимостей по слоям. Каждое приложение определяет свою цепочку слоёв; разрешены импорты из любого слоя правее по цепочке; обратные запрещены.
    2. Это не канонический FSD. Мы взяли лишь принцип разделения на layers, slices и segments.
    3. У каждого slice есть Public API: наружу импортируем только из `index.ts`. Экспортируем конкретные сущности (без `export *`). Слои, которые сразу делятся на сегменты (обычно `shared/`, иногда `app/`), — исключение: `index.ts` там избыточен.
    4. Имена файлов внутри slice/segment — по смыслу, без префикса slice’а: контекст задаёт путь. Пример: `.../meal-log/domain/analysis.ts`, не `.../meal-log-analysis.ts`.
    5. Между slices одного слоя прямые зависимости запрещены. Если нужно "склеить" два slice — делаем композицию в более верхнем слое.
    6. Если нужно использовать поведение соседнего slice — применяем Dependency Inversion: потребитель описывает контракт, а реализацию подключаем в слое выше через параметры/адаптер. Так не тянем чужие реализации и избегаем циклов.
    7. Если код "подходит сразу всем" и его тянут разные части проекта — не создаём `utils/helpers`. Такой код выносим в `lib/{name}` и организуем как отдельный внутренний пакет с единой ответственностью. Публикация в npm опциональна; README и тесты — целевое состояние (добавятся позже), но уже на старте обязателен понятный нейминг, границы пакета и Public API.
  </app-architecture>
